# Karaoke Player DB 스키마 호환성·복구 스펙

- 작성일: 2026-09-15
- 연관 스펙: `../draft/000-karaoke-app-spec-draft.md`, `006-track-pitch.md`
- 대상: 000 §4.3 데이터 레이아웃·S3 라이브러리의 버전 보호와 업그레이드 복구
- 상태: 구현 완료 (자동 검증 통과, 패키징 앱 수동 확인 대기)

이 문서는 000의 SQLite 라이브러리 저장에서 스키마 버전 검사, 마이그레이션 원자성, 백업과 실패 안내를 분리해 다룬다. CI·릴리즈·자동 업데이트는 후속 범위다.

## 1. 목표와 비목표

```text
앱이 지원하지 않는 DB를 만나거나 업그레이드에 실패하면 기존 라이브러리를 보존하고 원인과 다음 행동을 안내하며, 정상 업그레이드 후에는 기존 곡과 설정값을 그대로 읽는다.
```

| 영역      | 목표                                                                   |
| --------- | ---------------------------------------------------------------------- |
| 호환성    | DB 버전을 쓰기 작업 전에 검사하고 미래 버전을 거부한다                 |
| 원자성    | 시작 버전에서 지원 버전까지의 변경을 전부 성공하거나 전부 취소한다     |
| 백업      | 기존 DB 변경 전에 WAL에 있는 커밋까지 포함한 검증 가능한 백업을 남긴다 |
| 실패 처리 | 준비되지 않은 DB로 복구 작업·IPC·sidecar 작업을 시작하지 않는다        |

| 비목표                                              | 이유                                                                  |
| --------------------------------------------------- | --------------------------------------------------------------------- |
| 새 스키마·기능 컬럼 추가                            | 현재 v8의 데이터 계약을 보호하는 작업이다                             |
| 자동 다운그레이드·자동 백업 덮어쓰기 복원           | 백업 이후 데이터와 곡 파일을 잃을 수 있어 명시적 복구 절차로 분리한다 |
| 곡 파일·설정 전체 백업과 복구 UI                    | 이 스펙의 백업은 스키마 변경 직전 DB 스냅샷이다                       |
| 손상 DB·불명확한 과거 부분 마이그레이션의 추정 복구 | 버전을 추측해서 진행하지 않고 보존·안내한다                           |

## 2. 성공 기준

1. `user_version > SCHEMA_VERSION`인 DB를 열면 `DB_SCHEMA_TOO_NEW`로 중단한다. 스키마·행·`user_version`·journal mode를 변경하지 않고 마이그레이션·상태 정리·곡 파일 복구를 호출하지 않는다.
2. DB가 없는 신규 설치는 v8을 생성한다. 유효한 v1–v7 fixture는 v8로 이전하며 기존 ID·메타·순서·가이드 종류·볼륨을 보존하고 추가 컬럼의 기존 기본값을 적용한다. v8 재개방은 마이그레이션·백업을 수행하지 않는다.
3. 기존 DB 마이그레이션 전 백업을 재개방하면 시작 `user_version`과 전체 행이 일치하며, 아직 checkpoint되지 않은 WAL의 커밋도 포함된다. 백업 생성·검증 실패 시 원본 변경을 시작하지 않는다.
4. 마이그레이션의 중간 DDL·데이터 변환·최종 버전 기록에 오류를 주입하면 전부 롤백된다. 실패 후 재개방 시 시작 스키마·데이터·버전이 유지되고, 정상 재시도는 중복 컬럼 오류 없이 성공한다.
5. 프로세스를 commit 전·후에 강제 종료한 fixture는 재개방 시 각각 이전 상태·완료 상태로 복구되며, 중간 버전이나 부분 컬럼 상태가 노출되지 않는다.
6. 미래 버전·백업 실패·migration 실패·손상·사용 중 오류를 구분해 앱에서 안내한다. DB와 백업 위치를 확인할 수 있고 앱을 종료할 수 있으며, 오류 후 DB 핸들·백그라운드 작업이 남지 않는다.
7. 같은 데이터 디렉터리의 두 앱이 동시에 초기화하지 못한다. 쓰기 연결에서 버전을 재확인하며 잠금 획득·검증 실패는 제한된 시간 내 오류로 끝난다. 백업과 migration 사이의 지원되지 않는 외부 쓰기 경합은 진행하지 않는다.
8. v0은 비어 있는 DB만 신규 초기화한다. 사용자 테이블이 있는 v0, 음수 버전, 버전과 필수 구조가 불일치하는 DB는 보존하고 거부한다. 검증된 백업을 별도 경로에 복원해 재개방하는 절차가 테스트·문서로 제공된다.

## 3. 전제 조건

| 전제                                  | source of truth / 확인 방법                                             |
| ------------------------------------- | ----------------------------------------------------------------------- |
| 현재 지원 버전은 8                    | `src/main/library/LibraryStore.ts`의 `SCHEMA_VERSION`; 006의 pitch 컬럼 |
| 생성자에서 WAL 설정 후 migration 수행 | 같은 파일의 constructor·migrate; 마지막에 버전을 무조건 기록한다        |
| 초기화 직후 상태와 파일 복구가 실행됨 | `src/main/index.ts`의 `failStaleSeparating`, pair/edit 복구 호출        |
| SQLite는 WAL 사용                     | `LibraryStore.ts`; 살아 있는 DB 파일만 복사하는 백업은 채택하지 않는다  |
| 기존 마이그레이션 호환성 유지         | `src/main/library/__tests__/LibraryStore.test.ts`와 과거 버전 fixture   |

SQLite의 `user_version`은 앱이 관리하는 값이다. 백업은 SQLite가 제공하는 일관된 스냅샷 방식으로 만든다. [PRAGMA 문서](https://www.sqlite.org/pragma.html#pragma_user_version), [Backup 문서](https://www.sqlite.org/backup.html)

## 4. 기능 범위

### 4.1 초기화와 버전 분기

DB 준비를 명시적인 완료·실패 단계로 분리한다. 기존 파일은 read-only 사전 검사로 버전을 읽으며, 미래 버전 거부 전에는 WAL 전환, checkpoint, DDL/DML, 버전 기록을 하지 않는다. WAL을 무시하는 immutable 연결로 검사하지 않는다. read-only 접근이 불가능하면 쓰기 재시도로 우회하지 않고 오류로 끝낸다. SQLite가 필요로 하는 SHM 등 잠금 보조 파일 변화와 앱의 논리적 데이터 변경은 구분한다.

미래 버전은 현재 앱의 테이블 구조 검사보다 먼저 거부한다. 앱 버전과 DB 스키마 버전은 별개이며, 이번 보호 기능 때문에 v8을 올리지 않는다. 기존 v1–v8 각각의 필수 구조를 검사하고, 과거부터 남은 부분 migration을 임의로 완성하거나 버전을 낮추지 않는다.

단일 앱 인스턴스를 DB 준비 전에 확보하고, 지원되는 쓰기 연결을 연 뒤 버전·구조를 다시 검사한다. 백업부터 migration까지 다른 앱 쓰기를 배제한다. SQLite 잠금과 일관성 검사로 외부 writer가 끼어들 수 있는 구간을 닫으며, 버전 재검사만으로 동일 버전 DML까지 방지했다고 간주하지 않는다. 잠금 대기는 최대 5초이며 실패 시 `DB_BUSY`로 중단한다. 구현 방식은 자유지만 성공 기준 7의 경합 실험으로 증명한다.

### 4.2 백업과 migration

- 유효한 기존 구버전 DB에만 `<userData>/backups/db/` 아래 고유 이름으로 migration 전 백업을 만든다. 이름·메타에 시작/목표 버전, 앱 버전, UTC 시각, 고유 ID를 기록한다.
- SQLite backup API 등 WAL을 포함하는 스냅샷을 임시 파일로 작성하고 연결을 닫은 후 `quick_check`, 시작 버전, 필수 구조를 확인해 완료 파일로 확정한다. 열린 DB를 `copyFile`로 복사하지 않는다.
- 디스크 부족·권한·백업 검증 오류 시 migration은 시작하지 않는다. 이전 정상 백업은 덮어쓰지 않는다. 이 범위에서는 완료 백업을 자동 삭제하지 않는다.
- 현재 버전까지의 DDL·데이터 변환·최종 `user_version` 기록을 하나의 트랜잭션으로 실행한다. 기존 단계별 중첩 transaction은 전체 원자성 계약에 맞게 정리한다.
- 최종 버전은 모든 단계와 구조 검사가 성공한 뒤 같은 transaction에서 기록한다. 이미 현재 버전이면 버전을 다시 쓰지 않는다.
- migration은 DB 내부 변경만 한다. 곡 파일 이동·삭제는 transaction에 섞지 않고 기존 파일 복구는 DB 준비 성공 후에만 수행한다.
- 실패 시 rollback과 핸들 정리를 보장한다. rollback 자체가 실패하거나 DB 손상이 의심되면 보존 후 종료하며 빈 DB로 대체하지 않는다.

### 4.3 사용자 안내와 복구

Main의 시작 실패 경로에서 native dialog 등 렌더러 DB 의존성이 없는 방식으로 안내한다. `DB_SCHEMA_TOO_NEW`, `DB_BACKUP_FAILED`, `DB_MIGRATION_FAILED`, `DB_INVALID`, `DB_BUSY`를 안정된 오류 코드로 둔다.

미래 버전 안내는 발견 버전·앱 지원 버전과 더 최신 앱이 필요함을 표시한다. 다른 실패는 원본을 보존했다는 사실이 확인된 범위에서만 안내하고, 데이터/완료 백업 폴더 열기와 종료를 제공한다. 자동 삭제·초기화·자동 복원 버튼은 두지 않는다. 시작 실패 후 서비스 등록, sidecar 실행, `failStaleSeparating`, 임포트 복구를 진행하지 않는다.

복구 문서는 다음을 포함한다: 모든 앱 종료 → 원본 DB와 WAL/SHM 보존 → 선택 백업의 버전·무결성을 별도 경로에서 검사 → 백업에 맞는 앱으로 별도 복사본 확인 → 사용자가 복원을 결정한 경우에만 원본 교체. 기존 WAL/SHM을 복원한 DB에 붙이지 않는다. DB 백업은 `tracks/`를 포함하지 않으며 백업 이후 파일 변경과의 일치, 전체 라이브러리 복원을 보장하지 않는다고 명시한다. 절차 본문은 [`docs/db-recovery.md`](../db-recovery.md)다.

## 5. 검증 방법

아래 테스트 디렉터리는 D1·D2의 신규 산출물이며 현재 존재하는 테스트로 오인하지 않는다.

```bash
# 기준 1–8: 과거 fixture·백업·오류·경합·프로세스 종료/재개방
pnpm exec vitest run src/main/library/__tests__/LibraryStore.test.ts src/main/library/__tests__/db src/main/__tests__/startup
# 기존 라이브러리 동작 회귀와 시작 API 타입
pnpm test
pnpm typecheck
```

- fixture는 실제 사용자 DB가 아닌 합성 DB를 쓴다. 미래 버전 거부는 스키마·행·버전·journal mode 비교와 후속 서비스 미호출로 검증한다.
- WAL fixture는 writer 연결을 유지해 checkpoint 이전 커밋이 있는 상태로 백업 검사를 한다. 종료 실험은 자식 프로세스에 결정적 중단 지점을 두고 수행한다.
- 수동: 패키징 앱에서 미래 버전·디스크/백업 권한 실패 안내와 종료, 기존 곡이 있는 구버전 복사본의 업그레이드·재시작·재생을 확인한다. 실제 사용자 DB로 고장 주입하지 않는다.
- 복구 절차 문서: [`docs/db-recovery.md`](../db-recovery.md)
