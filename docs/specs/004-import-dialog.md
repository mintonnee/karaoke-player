# Karaoke Player 가져오기 팝업 스펙

- 작성일: 2026-09-12
- 연관 스펙: `000-karaoke-app-spec-draft.md`, `001-packaging-distribution.md`, `002-bpm-key-analysis.md`, `003-player-layout.md`
- 대상: 000 §2 로컬 임포트 목표·§5 S1.3, 001 §4.3 URL 입력 UI 확장
- 상태: 스펙 작성 완료, 구현 미착수

이 문서는 000의 음원 가져오기와 001의 URL 가져오기를 하나의 팝업으로 통합하고, 스템 분리 없이 MR과 가이드 파일을 등록하는 범위를 다룬다. 사용자는 두 번째 파일로 보컬 전용 파일과 반주가 포함된 AR 파일을 모두 지원하고 파일 종류를 선택하도록 요청했다. 이 문서의 신규 동작은 구현 목표이며 현재 구현 상태를 의미하지 않는다.

## 1. 목표와 비목표

```text
사용자는 가져오기 팝업에서 일반 음원 1개, MR과 가이드 파일 2개, YouTube URL 중 하나를 선택하여 한 곡을 등록하고, 일반 음원과 YouTube는 스템 분리 후, 두 파일은 분리 없이 준비 후 재생할 수 있다.
```

| 영역        | 목표                                                                                 |
| ----------- | ------------------------------------------------------------------------------------ |
| 진입점      | `+ 가져오기`로 앱 내부 모달 팝업을 열고 방식과 처리 여부를 선택 전에 보여준다.       |
| 일반 음원   | 파일 1개를 받아 기존 Demucs 스템 분리를 수행한다.                                    |
| 두 파일     | MR 1개와 가이드 1개를 역할별로 지정하여 한 곡으로 등록하며 Demucs를 호출하지 않는다. |
| 가이드 종류 | `보컬만 있는 파일`과 `AR (반주+보컬)`을 구별해 저장하고 재생 방식에 반영한다.        |
| YouTube     | URL 1개를 받아 기존 다운로드 후 스템 분리 흐름으로 연결한다.                         |
| 일관성      | 오류·중복 제출·재시작으로 불완전한 곡이 재생 가능 상태가 되지 않는다.                |

| 비목표                                              | 제외 이유                                                                                  |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 여러 곡 일괄 가져오기·폴더·재생목록 가져오기        | 이번 요청은 한 번에 일반 음원 1개 또는 한 곡의 파일 2개 또는 URL 1개다.                    |
| MR/AR 자동 식별·AR에서 보컬 추출·MR과 AR 차감       | 사용자가 종류를 선택하며 두 파일 방식에서는 스템 분리를 하지 않는다는 요청을 따른다.       |
| 서로 다른 편집본 자동 정렬·템포 보정·음량 자동 매칭 | 입력 파일의 기준 시각과 편집이 같아야 한다. 시간·음량 보정은 가져오기 역할을 넘어선다.     |
| URL 다운로드 엔진·배포 채널·부트스트랩 변경         | 001의 기존 capability와 준비 절차를 유지한다. 두 파일 방식도 기존 앱 초기 준비는 필요하다. |
| 새로운 믹서 레이아웃·효과·추가 스템                 | 003의 사이드 컬럼을 유지하며 파일 의미에 따른 컨트롤만 조정한다.                           |

## 2. 성공 기준

1. `+ 가져오기`를 누르면 팝업에 `일반 음원 1개`, `MR + AR / 가이드 파일 2개`, `YouTube URL`이 표시되고 각각 `스템 분리 진행`, `스템 분리 안 함`, `스템 분리 진행` 설명이 보인다. URL 미지원 실행에서는 기준 10을 적용한다.
2. 일반 음원 방식은 지원 파일 정확히 1개일 때만 제출할 수 있다. 성공하면 라이브러리에 한 곡이 추가되고 기존 `imported → separating → ready` 흐름을 따른다.
3. 두 파일 방식은 MR 슬롯과 가이드 슬롯에 각각 파일 1개를 넣고 가이드 종류를 선택해야 제출된다. 정상 입력은 한 곡으로 등록되고 `separate` 호출 횟수와 Demucs 모델 로드 횟수는 모두 0이다.
4. 파일 누락·같은 실제 파일 중복 지정·미지원 형식·손상·비정상 길이·길이 제한 초과·허용 길이 차이 초과를 Main/sidecar에서 거부하고 해당 역할과 사유를 표시한다. 실패한 두 파일 입력은 라이브러리에 곡이나 재생 가능한 부분 산출물을 남기지 않는다.
5. `보컬만 있는 파일`은 MR과 함께 재생되며 기존 보컬 볼륨·뮤트가 동작한다. `AR (반주+보컬)`은 MR/AR 선택에 따라 한 소스만 출력되고 전환 전후 재생 위치·루프·키가 유지된다.
6. 두 파일 곡은 앱 재시작 후 종류와 메타데이터가 보존되고 원본 파일을 이동한 뒤에도 앱 내부 파일로 재생된다. 기존 DB 곡은 마이그레이션 후 기존 보컬 혼합 방식으로 재생된다.
7. 일반 파일·YouTube 등록 접수 후 팝업은 닫히고 라이브러리에서 분리 진행을 확인할 수 있다. 두 파일은 준비·저장이 끝난 뒤 닫힌다. 제출 처리 중 재제출·방식 변경·닫기가 차단되고 실패하면 입력을 보존해 수정·재시도할 수 있다.
8. 파일 드롭도 팝업으로 연결되어 즉시 임포트하지 않는다. 두 파일의 역할은 사용자가 확정한다. 라이브러리 행 정렬 드래그는 가져오기로 처리하지 않는다.
9. 팝업이 열린 동안 Tab 포커스가 팝업 안에 머물고 재생 단축키가 작동하지 않는다. 작업 시작 전 또는 실패 후 Escape/닫기는 입력을 버리고 기존 포커스로 돌아간다. 파일 선택창 취소는 기존 입력을 유지한다.
10. YouTube 지원 실행에서 URL 1개가 다운로드된 뒤 기존 분리 파이프라인으로 들어간다. 다운로드 실패는 팝업에 표시된다. `urlImport=false`에서는 001 기준 6에 따라 URL 선택지와 입력을 렌더링하지 않고 직접 IPC 호출도 거부한다.
11. 두 파일 곡의 BPM·키는 MR에서 분석되고, 가사 조회·검색 키·커버는 기존 서비스에 연결된다. AR 가사 정렬·전사는 실제 AR 파일을 사용하며 이를 보컬 단독 파일로 취급하거나 자동 분리하지 않는다. 부가 작업 실패로 `ready`를 되돌리지 않는다.
12. 두 파일 준비·저장 중 종료 또는 DB 실패를 주입해도 다음 실행에서 불완전한 `ready` 곡이 나타나지 않고 해당 작업의 임시 파일이 정리된다. 재생 중 다른 곡을 가져와도 현재 곡의 재생 상태는 바뀌지 않는다.

## 4. 기능 범위

### 4.1 팝업과 입력

- 별도 OS 창이 아닌 앱 내부 모달을 사용한다. 기존 URL 아이콘과 인라인 입력 진입점을 팝업으로 통합한다. 최초에는 방식 선택 화면을 보여준다.
- 일반 음원은 단일 파일 슬롯, 두 파일은 `MR (반주)`·`AR / 가이드 파일` 두 슬롯, YouTube는 URL 입력란을 보여준다. 파일명, 바꾸기, 제거, 제출, 닫기를 제공한다.
- 두 파일 방식의 가이드 종류는 `보컬만 있는 파일` / `AR (반주+보컬)` 라디오로 선택한다. 초기에는 미선택이며 선택 전에는 제출할 수 없다. 파일명으로 종류를 추측하지 않는다.
- 두 파일 입력 아래에 `같은 곡·같은 편집본이며 시작 시각이 맞는 파일을 선택하세요`를 표시한다. 보컬 전용은 `MR과 함께 재생`, AR은 `MR과 AR을 전환하여 재생`이라고 설명한다.
- 방식 변경 시 기존 방식의 입력과 오류를 비운다. 닫고 다시 열면 초기화한다. 제출 실패 시에는 입력을 보존한다. 배경 클릭은 팝업을 닫지 않는다.
- 파일 선택은 입력 채우기만 수행하고, 명시적인 `가져오기` 제출 전에는 복사·다운로드·DB 등록·분리를 시작하지 않는다.
- 파일 1개 드롭은 일반 음원 화면에 채운다. 파일 2개 드롭은 두 파일 화면의 미지정 목록에 보여주고 사용자가 MR/가이드 슬롯에 배정한다. 3개 이상이면 개수 오류만 표시한다. 슬롯 자체 드롭은 한 파일만 허용한다.
- URL은 공백을 제거한 HTTP(S) YouTube 동영상 URL 1개를 검증한다. `youtube.com`·`www.youtube.com`·`m.youtube.com`의 watch/shorts/live 동영상 경로와 `youtu.be` 단축 동영상을 지원한다. 호스트는 파싱한 값으로 비교한다. 재생목록 전용 URL은 거부하고 동영상에 붙은 목록 정보는 기존 `--no-playlist`로 무시한다.
- URL 선택지 노출은 001의 capability 계약을 유지한다. 따라서 지원 빌드에서는 3가지, 미지원 빌드에서는 로컬 2가지다. 배포 정책 변경은 이 스펙에 포함하지 않는다.

### 4.2 처리 경로와 상태

| 방식        | 처리 경로                                                                                | 팝업 완료 시점                       |
| ----------- | ---------------------------------------------------------------------------------------- | ------------------------------------ |
| 일반 음원   | 단일 파일 검증 → 기존 원본 복사·등록 → 분리 큐 → `ready`                                 | 등록 및 분리 작업 접수 성공          |
| MR + 가이드 | 양쪽 검증 → 앱 임시 영역으로 복사 → 디코딩·형식 통일 → 파일 확정·DB 한 곡 등록 → `ready` | 두 재생 파일과 DB 등록 완료          |
| YouTube     | URL 검증 → 기존 다운로드 → 일반 음원 분리 경로                                           | 다운로드 및 등록·분리 작업 접수 성공 |

- 두 파일 준비에 별도 sidecar 명령 `prepare-pair`를 추가한다. 이는 **제안하는 신규 계약**이며 현재 명령이 아니다. 입력은 MR·가이드 경로와 출력 디렉토리, 결과는 출력 파일 경로와 최종 duration이다. 일반 파일용 `importFiles`를 두 번 호출하는 구현은 금지한다.
- `prepare-pair`는 Demucs의 Separator·모델·GPU를 초기화하지 않는다. 디코딩·리샘플링은 가능하며 앱 부트스트랩, 가사 처리, BPM·키 분석의 존재와 스템 분리 여부는 구분한다.
- 준비 작업은 기존 공용 `JobQueue`로 직렬화한다. 팝업에는 `준비 대기`, `파일 확인`, `파일 준비`, `저장` 단계를 표시한다. 측정할 수 없는 단계에는 임의 백분율 대신 불확정 진행 표시를 쓴다.
- 작업 식별자로 진행 이벤트와 결과를 연결한다. 하나의 제출이 처리되는 동안 앱의 다른 가져오기 진입점·드롭도 차단한다. Main은 중복 활성 요청을 거부하고 Renderer 버튼 연타 방지만 믿지 않는다. 일반 파일의 분리 큐 접수 후에는 다음 가져오기를 허용한다.
- 작업 시작 후 Escape·닫기·방식 변경을 비활성화한다. OS 종료로 중단된 작업 복구는 §4.4를 따른다. 작업 취소 UI는 추가하지 않는다.
- 기존 분리 실패는 라이브러리와 오류 센터에서 알린다. 등록 전 실패는 팝업의 입력 역할 옆에 알리고 기존 오류 센터에도 중복 없이 기록한다.

### 4.3 두 파일 검증과 형식 통일

- Main에서 요청 종류·필드 타입·정확한 파일 개수·가이드 종류를 검사한다. 파일 경로는 로컬 일반 파일이어야 한다. 확장자 검사와 실제 디코딩 검사를 모두 수행한다.
- MR과 가이드가 같은 실제 파일이면 거부한다. Windows 경로 대소문자·심볼릭 링크·하드 링크를 고려한 파일 식별로 우회 중복을 막는다.
- 각 파일의 길이는 유한한 양수이고 `maxDurationSec` 이하여야 한다. probe 결과와 최종 디코딩 길이를 모두 확인한다.
- 길이 차이는 디코딩 후 기준 **100 ms 이하**를 허용한다. 이는 컨테이너 길이·끝부분 차이를 위한 제품 허용치이며 동기화 정확도 보장이 아니다. 초과 시 양쪽 길이와 차이를 표시하고 거부한다.
- 출력은 44,100 Hz, stereo PCM WAV로 통일한다. mono는 양쪽 채널에 복제하고 3채널 이상은 명시적으로 거부한다. 실제 지원 코덱은 구현 시 번들 환경에서 확인한다. 디코딩 실패 시 확장자만 `.wav`로 바꿔 성공 처리하지 않는다.
- 출력 시작 시각을 이동하지 않는다. 허용 범위 안의 끝부분 차이는 짧은 쪽 뒤에 무음을 붙여 두 파일의 프레임 수를 동일하게 만든다. 트랙 duration은 통일한 프레임 수에서 계산한다. 피크/음량 정규화·앞부분 무음 제거·타임 스트레치는 수행하지 않는다.
- 같은 길이여도 서로 다른 곡이나 오프셋이 있는 파일을 자동 판별하지 않는다. 입력 안내와 수동 청취 검증으로 이 한계를 분명히 한다.

### 4.4 저장 계약과 실패 복구

- 스키마 v4 다음 마이그레이션에서 `import_kind = separated | paired`와 `guide_kind = vocal_only | full_mix`를 추가하고 `Track`에 노출한다. 기존 행은 `separated`·`vocal_only`로 채운다. 일반 음원과 YouTube는 모두 `separated`다. `separated/full_mix` 조합은 허용하지 않는다.
- 두 파일은 하나의 track ID를 사용한다. MR 출력은 `inst.wav`, 보컬 전용 출력은 `vocal.wav`, AR 출력은 `guide.wav`로 저장한다. AR을 `vocal.wav`라는 이름으로 숨기지 않는다.
- 두 원본 복사본은 `source.<ext>`(가이드 원본)와 `source-inst.<ext>`(MR 원본)로 보관한다. `sourcePath`는 가이드 원본 입력 경로를 기록하지만 재생에는 사용하지 않는다. 이 구성이 기존 CoverService의 `source.<ext>` 조회를 유지한다.
- 제목·아티스트·앨범은 가이드 태그 → MR 태그 순으로 선택하고, 제목이 없으면 MR 파일명을 사용한다. duration은 §4.3의 최종 값이다. 사용자는 기존 메타 편집으로 수정할 수 있다.
- `meta.json`은 두 파일의 역할·종류·입력 파일명·준비 버전·시각을 기록한다. 두 파일 곡에 Demucs 모델 실행 기록을 만들지 않는다. 종류 판정의 기준은 DB이며 JSON은 처리 기록이다.
- 준비 중에는 라이브러리 행을 만들지 않는다. 작업 전용 임시 디렉토리에서 두 출력과 메타를 검증하고 최종 트랙 디렉토리로 이동한 뒤, 한 DB 트랜잭션으로 `ready` 행을 생성한다. 그 후에만 결과/알림을 보낸다.
- DB 실패 시 해당 작업이 만든 파일을 정리한다. 프로세스 종료에 대비한 작업 기록을 두고, 시작 시 완료 DB 행이 있으면 보존하며 미완료 작업에 속한 임시/미등록 디렉토리만 정리한다. 일반 곡이나 사용자 입력 파일을 정리 대상으로 삼지 않는다. 파일 이동과 DB 트랜잭션을 하나의 원자적 연산이라고 가정하지 않는다.

### 4.5 재생·가사·분석 연결

- `TrackFiles`를 가이드 종류를 포함한 계약으로 확장해 Main이 `vocal.wav` 또는 `guide.wav`를 선택한다. AudioEngine의 두 번째 입력도 보컬 전용이라고 가정하지 않는 이름으로 갱신하고 상위 000 §4.1의 실제 인터페이스를 구현 시 함께 맞춘다. 필수 파일이 없으면 `ready`여도 재생을 거부한다.
- `vocal_only`는 기존 MR+보컬 혼합, 볼륨, 뮤트, 기본 보컬 -20 dB 동작을 유지한다.
- `full_mix`는 믹서에 `MR / AR` 전환을 표시한다. 곡을 새로 로드하면 MR이 기본이다. 정상 출력 구간에서 선택하지 않은 소스의 게인은 0이며 MR+AR을 합산하지 않는다.
- AR 전환 시 두 소스의 공통 재생 시계와 위치를 유지한다. 시크·루프·키 변경도 양쪽에 동일하게 적용한다. 클릭 방지는 기존 엔진의 게인 램프를 이용하되 이전 소스를 음소거한 뒤 새 소스를 올리는 순서로 겹침을 피한다.
- AR 곡에서는 `보컬` 페이더 명칭을 `AR`로 바꾸고 AR 전체 음량을 조절한다고 표시한다. 선택된 쪽의 페이더만 활성화하며 MR/AR 개별 뮤트는 숨긴다. 메인 볼륨·메인 뮤트는 공통 적용한다. AR 초기 게인은 0 dB로 두고 보컬 전용 -20 dB 설정과 분리한다.
- 단축키 `V`는 AR 곡에서 MR/AR 전환에 대응한다. 기존 반주 뮤트/볼륨·보컬 볼륨 단축키도 비활성 소스를 켜지 않도록 선택된 채널 규칙을 따르고 단축키 도움말에 반영한다. 곡 종류 전환 시 AR 상태가 보컬 전용 곡의 게인에 누출되지 않는다.
- LRCLIB 가사 조회·검색 키·커버 작업은 두 파일 등록 후 기존 서비스로 요청한다. BPM·키 분석은 `ready` 알림 뒤 MR인 `inst.wav`를 대상으로 큐에 넣는다. 분석 실패가 재생을 막아서는 안 된다.
- 가사 정렬·전사는 가이드 종류에 따라 `vocal.wav` 또는 `guide.wav`를 사용한다. AR은 반주가 포함된 입력이므로 해당 작업 화면에 정확도가 낮아질 수 있음을 표시하며, 자동 Demucs 분리로 보완하지 않는다. 기존 동기 가사와 수동 보정은 그대로 지원한다.

## 5. 검증 방법

이번 산출물은 문서다. 아래 기능 검증은 **후속 구현 시 실행할 계획**이며 현재 통과한 것으로 간주하지 않는다. 새 테스트가 아직 없을 때 기존 테스트 통과만으로 신규 기준을 완료 처리하지 않는다.

```bash
# 스펙 형식 검증
pnpm exec prettier --check docs/specs/004-import-dialog.md

# 구현 후 전체 계약·회귀의 공통 전제 (기준 1–12)
pnpm typecheck
pnpm lint
pnpm test

# 구현 후 미디어 변환 검증 (기준 3·4·6): 신규 pair 테스트 포함
uv run --project sidecar --frozen pytest sidecar/tests

# 렌더러/메인 빌드 및 수동 검증 준비 (기준 1–12의 필요조건)
pnpm build
pnpm dev
```

- 서비스/IPC 테스트: 입력 종류·개수·URL 검증, 두 파일 실패 시 DB/파일 잔여물 없음, 중복 제출, 큐 대기, 작업 ID가 다른 지연 이벤트, DB 실패, 재시작 복구, v4 마이그레이션, AR 파일 경로와 부가 서비스 호출을 검증한다. 일반/URL의 분리는 정확히 한 번 큐에 들어가고 paired의 `separate`·모델 로드는 0회임을 스파이와 sidecar 테스트로 검증한다 (기준 2–4·6·7·10–12).
- 미디어 테스트: mono/stereo·서로 다른 샘플레이트·지원 확장자·손상 파일·다채널을 사용한다. 길이 차이 99/100/101 ms와 최대 길이 경계, 출력 프레임 수·시작 샘플 위치·무음 패딩을 검사한다. 모델 캐시가 없는 준비 환경에서도 paired 명령이 모델 다운로드 없이 끝나는지 확인한다 (기준 3·4).
- UI 수동 검증: 각 방식의 정상 등록·실패 후 수정·선택창 취소·파일 역할 교환·드롭 개수 오류·Tab/Shift+Tab·Escape·버튼 연타·처리 중 닫기·팝업 중 재생 단축키 차단을 확인한다. Node 환경 테스트만으로 포커스나 네이티브 파일 대화상자 동작을 검증했다고 주장하지 않는다 (기준 1–3·7–9).
- 오디오 검증: 합성 신호로 보컬 전용 혼합과 AR 비선택 소스 무출력을 확인하고, 실제 동일 편집 MR/AR 및 MR/보컬 파일로 전환·음량·뮤트·시크·루프·키 변경을 청취한다. 서로 다른 편집본의 동기화는 보장 대상으로 삼지 않는다. 보컬 전용 곡 ↔ AR 곡 전환 시 설정 누출도 확인한다 (기준 5·6).
- 통합/복구 검증: 원본 파일을 이동한 뒤 재시작·재생·가사 정렬·MR 분석을 수행한다. 준비 중, 파일 확정 뒤 DB 등록 전, DB 등록 뒤 응답 전 각각 종료하여 DB와 파일 일관성을 확인한다. 기존 재생 중 가져오기가 재생 위치를 바꾸지 않는지 확인한다 (기준 6·11·12).
- URL 검증: capability 지원/미지원 실행을 각각 확인하고, 라이브 YouTube 1건의 다운로드 → 분리 → 재생과 잘못된 URL·네트워크 실패를 구분해 기록한다. mock 다운로드 성공은 실제 YouTube 동작 증거가 아니다 (기준 10).
