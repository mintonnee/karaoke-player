# Karaoke Player 알림 센터 스펙

- 작성일: 2026-09-17
- 연관 스펙: `008-runtime-dependency-lock.md`, `003-player-layout.md`, `002-bpm-key-analysis.md`
- 대상: 008 §4.5 준비 상태·실패 UI와 기존 사이드 툴바 오류 기록 창의 통합
- 상태: 구현 완료 (자동 검증 통과, 실제 앱 수동 확인 대기)

이 문서는 008의 런타임·모델 준비 표시를 검색창 아래에서 알림 센터로 옮기고, 기존 오류 기록·보고 기능과 함께 제공하는 범위를 다룬다. 노래별 분리·가사 작업 화면 자체는 개편하지 않는다.

## 1. 목표와 비목표

```text
사용자는 노래 목록의 위치 변화 없이 알림 버튼에서 준비 중 여부와 오류를 확인하고, 알림 창에서 현재 준비 단계와 오류 상세·가능한 복구 동작을 확인할 수 있다.
```

| 영역 | 목표                                                                 |
| ---- | -------------------------------------------------------------------- |
| 배치 | 검색창 아래 준비 배너를 없애고 기존 알림 버튼과 모달로 통합한다      |
| 진행 | 다운로드·검증·환경 구성·모델 준비의 현재 상태를 표시한다             |
| 오류 | 세션 오류 기록, 읽음 배지, 개별/전체 지우기와 GitHub 보고를 유지한다 |
| 복구 | 실제 실행 가능한 동작에만 재시도를 제공하고 기존 곡 재생을 유지한다  |

| 비목표                                  | 이유                                                                          |
| --------------------------------------- | ----------------------------------------------------------------------------- |
| 모든 백그라운드 작업의 통합 작업 관리자 | 이번 범위는 기존 준비 상태와 오류 기록의 이동·통합이다                        |
| Windows 알림·토스트·자동 팝업           | 재생·검색을 방해하지 않는 명시적 열기 방식을 사용한다                         |
| 성공 이력 영구 저장·DB 마이그레이션     | 진행 표시는 현재 상태, 오류 기록은 기존처럼 앱 세션 단위다                    |
| 작업 취소·범용 작업 재실행 IPC          | 원래 작업별 취소·재실행 계약이 필요하며 UI 이동과 분리한다                    |
| 다운로드 바이트 계측 신규 구현          | 현재 BootstrapState에는 정량 진행률이 없어 단계와 불확정 진행 표시를 사용한다 |

## 2. 성공 기준

1. 라이브러리가 비어 있거나 검색 결과가 0개여도 검색창 아래에 준비 패널/상태 줄이 나타나지 않는다. 준비 상태 변경 전후 검색창·노래 목록의 배치가 유지된다.
2. 기존 종 모양 버튼으로 제목이 `알림`인 창을 연다. 상단에는 현재 준비 상태, 하단에는 오류 기록이 표시되며, 준비 시작·완료·오류만으로 창이 자동으로 열리지 않는다.
3. 준비 중이면 버튼에 진행 표시가 나타난다. 읽지 않은 오류 수는 별도 숫자 배지로 표시하고 10건 이상은 `9+`로 표시한다. 동시 존재 시 둘 다 구분되며 진행 갱신은 오류 수를 늘리지 않는다.
4. 단계 전환은 하나의 현재 상태를 갱신한다. 완료 후 진행 표시와 진행 카드는 사라진다. 모델 준비 종료를 원래 분석·가사 작업 완료로 표시하지 않는다. 실패 시 회전 표시가 멈추고 실패 정보가 보존된다.
5. 초기 상태 조회와 실시간 이벤트가 엇갈려도 과거 응답으로 최신 상태를 덮어쓰지 않는다. 창을 닫았다 열어도 현재 상태가 정확하며 구독 중복으로 오류가 증가하지 않는다.
6. 런타임 초기화 실패는 세션 오류 기록에 한 번 남는다. 같은 실패 상태의 반복 수신·모달 재열기는 중복 오류를 만들지 않는다. 명시적으로 다시 시도한 작업의 새 실패는 별도 기록으로 남는다.
7. 모델 준비 실패는 원래 작업의 AppErrorReport로 기록하며 준비 상태로부터 같은 오류를 다시 생성하지 않는다. 실패를 `준비 완료` 알림으로 바꾸지 않는다.
8. 오류 지우기·읽음 처리는 실제 진행 상태나 실패 상태, 런타임 사용 가능 여부를 바꾸지 않는다. 알림창을 열면 현재 오류가 읽음 처리되고, 열려 있는 동안 화면에 추가된 오류도 읽음 처리된다.
9. 런타임 재시도는 실제 재구성 가능한 현재 실패에만 제공한다. 클릭 중 중복 호출을 막고 결과를 표시한다. 모델/분석 오류에 bootstrap 재시도를 붙이지 않는다. 사용자 값·기존 곡·정상 캐시는 유지한다.
10. 준비 중 기존 곡 재생은 가능하고, 런타임이 필요한 작업의 기존 차단 규칙은 유지된다. 차단된 가져오기 등의 진입점에는 `환경 준비 중 · 알림에서 확인` 또는 실패 안내가 표시된다.
11. 오류가 없고 진행도 없으면 `새로운 알림이 없습니다.`를 표시한다. 전체 보고·전체 지우기는 오류에만 적용되며, GitHub 보고의 경로 가림과 사용자 최종 제출 방식이 유지된다.
12. 1040×600과 1440×900에서 모달이 화면 밖으로 나가지 않고 헤더·닫기·현재 상태를 유지한다. 오류가 많으면 오류 목록 내부만 스크롤한다. 키보드 열기·닫기, 포커스 복귀, 상태 읽기와 reduced-motion을 검증한다.

## 4. 기능 범위

### 4.1 배치와 시각적 우선순위

기존 `오류 기록` 모달을 `알림`으로 확장한다. 새 메뉴나 탭은 추가하지 않는다. 기존 사이드 툴바 위치를 유지한다.

```text
알림                               [닫기]
현재 상태
  모델 준비 중…                    [진행 표시]
  [상세 보기]

오류 기록              [전체 보고] [모두 지우기]
  00:12:03  BPM·키 분석
  모델을 준비하지 못했습니다.       [상세/보고/지우기]
```

- 헤더는 제목·닫기만 두고 오류 전용 동작은 오류 영역에 둔다. 오류가 없으면 오류 영역과 해당 동작을 숨긴다.
- 모달 폭은 520px, 높이는 480px를 기준으로 하고 뷰포트에서 상하좌우 24px 여백을 확보하도록 제한한다. 상태 유무로 외곽 크기가 바뀌지 않는다. 빈 상태에서는 불필요한 스크롤이 없다.
- 현재 상태 요약은 고정한다. 기술 상세는 접힌 영역으로 제공하고 펼쳐진 상세는 높이를 제한해 내부 스크롤한다. 전체 모달과 오류 목록이 함께 스크롤되지 않도록 한다.
- 사용자 메시지는 `실행 환경 다운로드 중`, `다운로드 파일 확인 중`, `실행 환경 구성 중`, `모델 준비 중`처럼 단계 중심으로 쓴다. `id=`, `stage=`, `retryable=` 및 로그는 상세에만 표시한다.
- 현재 aggregate 상태만으로 특정 모델이 유일하게 진행 중이라고 단정하지 않는다. 모델 준비 카드는 `모델 준비 중`으로 표시하고 논리 ID는 마지막 보고된 상세 정보로 한정한다. 개별 작업 수나 모델별 완료 목록을 추정하지 않는다.
- 검색창 아래 배너를 제거하면서 빈 목록 안내의 prepChrome 의존도 함께 제거한다. 최초 빈 라이브러리에는 기존 가져오기 안내와 작업 불가 사유를 제공한다.

### 4.2 상태·오류 데이터 계약

현재 준비 상태는 bootstrapStore, 오류 기록은 errorStore를 source of truth로 유지한다. 알림창을 열 때만 구독하는 구조로 바꾸지 않는다. 화면의 투영 상태와 실제 런타임 가용성은 분리한다.

| 입력                                             | 현재 상태 영역           | 버튼                             | 오류 기록                  |
| ------------------------------------------------ | ------------------------ | -------------------------------- | -------------------------- |
| 상태 미수신/idle                                 | `준비 상태 확인 중`      | 진행 표시                        | 추가하지 않음              |
| download/verify/env-prep 및 기존 copying/syncing | 해당 준비 단계           | 진행 표시                        | 추가하지 않음              |
| model-prep                                       | `모델 준비 중`           | 진행 표시                        | 추가하지 않음              |
| ready                                            | 숨김                     | 진행 표시 해제                   | 기존 기록 유지             |
| runtime error                                    | 현재 실패·가능한 재시도  | 진행 표시 해제, 미확인 오류 배지 | 시도당 한 번 기록          |
| 원래 작업의 AppErrorReport                       | bootstrap 현재 상태 유지 | 미확인 오류 배지                 | 기존 오류 수신 경로로 추가 |

- 최초 조회 전에 구독하고, 조회를 시작한 이후 실시간 이벤트를 받았다면 늦게 도착한 최초 응답을 적용하지 않는다. 구독 해제와 재마운트도 검증한다.
- 런타임 오류 기록용 source `runtime`과 표시명 `실행 환경`을 추가한다. bootstrapStore의 상태 수신 경계에서 런타임 실패 전이를 errorStore로 전달하며 렌더링 effect마다 기록하지 않는다.
- 비오류 상태에서 오류 상태로 전환될 때 한 번 기록한다. 최초 snapshot이 오류여도 한 번 기록한다. 오류 상태 반복 수신은 추가하지 않는다. 재시도를 새 시도로 구분하고, 비오류 전환 없이 재시도가 실패해도 새 실패를 기록한다.
- model-prep overlay는 진행 표시 전용으로 둔다. 모델 준비 실패의 기록 주체는 해당 작업 서비스다. 원래 서비스가 실패를 보고하는 기존 경로를 유지한다.
- 오류 기록은 최근 50건·세션 단위를 유지한다. 오류 목록 삭제 후에도 현재 실패 카드와 필요한 재시도 안내는 남는다. 상태 재수신만으로 지운 기록이 다시 생기지 않는다.
- 정상 준비 완료는 별도 성공 이력이나 미확인 배지를 생성하지 않는다. 다른 작업 오류가 들어왔다고 진행 중인 준비 표시를 없애지 않는다.

### 4.3 재시도와 기능 가용성

- 런타임 실패 카드에서만 `다시 시도`를 제공한다. `retryable`이 true이고 실제 bootstrap 재구성을 수행할 수 있을 때만 노출한다. manifest 누락 등 현재 구현의 no-op 재시도는 재시도 가능으로 표시하지 않도록 백엔드 상태도 맞춘다.
- 재시도 Promise 대기 중에는 버튼을 비활성화한다. IPC 거부나 다시 실패한 결과는 사용자에게 남기고 무한 진행 표시로 끝내지 않는다. 재시도 성공은 이전 오류 기록을 삭제하지 않는다.
- 오류 목록 항목에 공통 `다시 시도` 버튼을 만들지 않는다. 분리·가사 등은 기존 화면의 재실행 경로를 안내한다. 자동 BPM 분석 오류는 현재의 앱 재시작 백필을 안내하며, 준비 재시도가 분석을 다시 실행한다고 표시하지 않는다.
- `isRuntimeActionAllowed`·`isRuntimeReady`를 실제 차단 판단에 계속 사용한다. UI의 오류 읽음/삭제로 작업 가능 상태를 변경하지 않는다. model-prep 때문에 기존 허용 작업을 전부 차단하지 않는다.

### 4.4 접근성·기존 기능 유지

- 버튼의 접근성 이름은 `알림`, tooltip은 진행 여부와 미확인 오류 수를 요약한다. 장식 아이콘은 읽기에서 제외한다. 오류가 진행과 동시에 있으면 숫자 배지를 우선 인식할 수 있게 한다.
- 모달은 dialog 역할·제목 연결·초기 포커스·Tab 포커스 제한·Escape 닫기·닫은 뒤 종 버튼으로 포커스 복귀를 갖춘다. 바깥 영역 클릭 닫기는 기존 동작을 유지한다.
- 현재 단계는 polite 상태 영역으로 읽는다. 로그의 매 줄이나 단순 재렌더링을 반복 낭독하지 않는다. reduced-motion에서는 회전 대신 정적 진행 표식과 문구를 사용한다.
- 보고 동작은 오류 항목만 대상으로 한다. 현재 진행 메시지·일반 다운로드 로그를 전체 보고에 자동 포함하지 않는다. 기존 경로 가림·URL 제한을 유지하며 보고 제출은 브라우저에서 사용자가 한다.

## 5. 검증 방법

아래는 구현 후 실행할 검증 계획이다. 이 스펙 작성 시점에 신규 테스트나 UI가 존재한다고 주장하지 않는다.

```bash
# 기준 3–11: 상태 전이·오류 기록·재시도·보고 회귀 테스트 포함
pnpm test
# 기준 1–12: shared/main/renderer 계약과 빌드
pnpm typecheck
pnpm lint
pnpm build
# 기준 1–3·9·10·12: 실제 앱 수동 확인
pnpm dev
```

- 상태 fixture: 최초 snapshot 지연, 이벤트 선도, 반복 error, 재시도 실패/성공, 창 닫힘 중 실패, 오류 삭제 후 같은 상태 재수신, 모델 준비와 원래 작업 오류의 동시 발생을 검증한다.
- 읽음 fixture: 창 닫힘/열림 각각에서 신규 오류를 수신하고 배지·목록 반영을 확인한다. 50건 상한과 사용자 보고 내용의 경로 가림을 회귀 검증한다.
- 1040×600·1440×900에서 준비 중/오류/빈 상태/50건 오류/긴 메시지/상세 펼침을 확인한다. 검색 결과 0개와 최초 빈 라이브러리는 별도로 확인한다.
- 실제 앱에서 준비 중 검색·기존 곡 재생이 유지되는지, 검색창·목록이 움직이지 않는지, 런타임 불가 작업의 차단 안내가 보이는지 확인한다.
- 격리한 테스트 캐시에서 다운로드·검증 실패 및 runtime 재시도를 확인한다. 사용자 정상 캐시를 삭제해 실패를 만들지 않는다. 모델 작업 실패에는 잘못된 환경 재시도 버튼이 없는지 확인한다.
- 실제 앱·다운로드·키보드 검증을 수행하지 않았으면 테스트/빌드 통과와 구분해 미검증으로 기록한다.
