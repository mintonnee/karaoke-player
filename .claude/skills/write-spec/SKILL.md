# 스펙 작성 스킬

Broadcast Whiteboard의 스펙 문서(`docs/specs/`)를 작성·수정하는 규칙. 캐노니컬 템플릿과 인덱스는 `docs/specs/README.md`에 있다 — 작성 전에 반드시 읽고 템플릿 구조를 그대로 따른다.

## 파일 규칙

- 위치: `docs/specs/NNN-kebab-case-name.md`. 번호는 3자리, 기존 인덱스의 다음 번호를 사용한다. `000`은 프로젝트 개요(최상위 스펙)다.
- 새 스펙은 상위 스펙(대부분 `000`)의 성공 기준 하나 또는 기능 슬라이스 하나를 대상으로 분리한다. 헤더의 `연관 스펙:`에 상위 스펙 파일명을 백틱으로 적는다.
- 작성 후 반드시 두 가지를 갱신한다:
  1. `docs/specs/README.md` 인덱스 표에 한 줄 추가
  2. 상위 스펙에서 분리된 범위를 다루는 문장/표에 새 스펙 참조 추가 (예: "상세는 `001-project-init`")

## 섹션별 작성 원칙

템플릿 구조: 헤더 → 1. 목표와 비목표 → 2. 성공 기준 → 3. 전제 조건 → 4. 기능 범위 → 5. 검증 방법.

### 헤더

- 제목: `# Broadcast Whiteboard <기능 이름> 스펙`
- `작성일:`은 실제 오늘 날짜(YYYY-MM-DD). 날짜가 불확실하면 추측하지 말고 셸에서 확인한다: PowerShell `Get-Date -Format yyyy-MM-dd`, bash `date +%F`. `대상:`은 상위 성공 기준 또는 기능 슬라이스를 지목한다.
- 본문 첫 문장: "이 문서는 <상위 스펙>에서 <분리한 범위>를 다룬다." 다루지 않는 것도 한 문장으로 못박으면 좋다.

### 1. 목표와 비목표

- 검증 문장은 딱 1개, `text` 코드 블록. 사용자 관점 또는 runtime 관점에서 성공을 한 문장으로 쓴다. 구현 용어("X를 리팩터링한다")가 아니라 관찰 가능한 결과("X를 하면 Y가 보인다")로 쓴다.
- 목표 표는 영역별로 나눈다. 비목표 표에는 **제외 이유**를 반드시 적는다 — "v2 이후", "별도 스펙", "상위 스펙 결정 사항" 등 근거 없는 비목표는 쓰지 않는다.
- 상위 스펙 본문에 흩어져 있는 "불사용/불필요" 결정(예: CRDT 불사용)도 비목표 표로 끌어올린다.

### 2. 성공 기준

- 모든 기준은 관찰 가능해야 한다. "잘 동작한다" 금지. "X를 하면 Y가 exit 0/화면에 보인다/파일이 생성된다" 형태로 쓴다.
- 부정 조건도 실험 가능하게 쓴다 (예: "위반 import를 임시로 넣으면 lint가 exit 1 → 제거하면 exit 0").
- 번호는 이후 슬라이스 완료 판정과 §5 검증 명령이 참조하므로 안정적으로 유지한다.

### 3. 전제 조건

- 각 전제에 **source of truth 또는 확인 방법**을 적는다 (파일 경로, 설정 키, 포트, 버전 범위).
- 도구/버전 결정에 유보 조건이 있으면 함께 기록한다 (예: "vitest 4 업그레이드는 Forge plugin-vite가 vite 6+ 지원 이후").
- 레포의 실제 상태(package.json, 설정 파일)를 확인하고 쓴다. 기억으로 추측하지 않는다.

### 4. 기능 범위

- 하위 섹션(4.1, 4.2, …)으로 나눈다. 상위 스펙과 겹치는 내용은 복제하지 말고 "000 §4.2를 따른다" + 요약으로 참조한다.
- 구현 방식이 유동적인 부분은 "성공 기준이 우선, 구현 방식은 자유"를 명시해 스펙이 구현을 과잉 구속하지 않게 한다.

### 4.x 구현 슬라이스 (멀티 에이전트 감독용 경계)

구현 작업이 있는 스펙은 기능 범위 마지막 하위 섹션에 슬라이스 표를 넣는다:

| 슬라이스 | 산출물 | 소유(수정 가능) 경로 | 수정 금지 경로 | 선행 조건 | 상태 |

- **소유 경로는 슬라이스 간 겹치지 않게** 나눈다. 에이전트는 자신의 슬라이스가 소유한 경로만 수정한다.
- 공유 파일(`package.json`, `tsconfig.json`, 루트 설정)은 소유 슬라이스를 하나만 지정한다. 두 슬라이스가 같은 파일을 수정해야 하면 감독자가 순서를 정하고 병합한다.
- 선행 조건으로 순차/병렬 가능 여부가 드러나야 한다. 상태는 `완료 | 진행 중 | 미착수`로 유지하고, 완료된 슬라이스는 재작업 금지를 명시한다.
- 슬라이스 완료 판정은 성공 기준 번호 매핑으로 정의한다 (예: "S2 = 기준 1–2").
- 감독 규칙에 다음을 포함한다: 에이전트는 종료 전 §5 검증 명령 실행 + exit code 보고, 훅 우회(`--no-verify`, `LEFTHOOK=0`) 금지, git 상태 변경(commit/stage)은 감독자 또는 사용자만 수행.
- 이 슬라이스 표를 실제로 실행할 때는 `orchestrate-slices` 스킬을 사용한다.

### 5. 검증 방법

- `bash` 코드 블록에 실행 명령을 나열하고, 각 명령이 어떤 성공 기준 번호를 검증하는지 주석으로 매핑한다.
- 명령으로 검증할 수 없는 항목(수동 확인, 임시 코드 실험)은 블록 아래 불릿으로 절차를 적는다.

## 문체

- 한국어로 쓰되 코드 식별자, 파일명, 도구명, 명령은 원문 유지.
- 단정형 종결("한다", "다룬다"체). 결정 사항은 근거 또는 참조와 함께 기록한다.
- 범위 표기는 물결표(`~`)를 쓰지 않고 en dash(`–`)를 쓴다(예: "기준 1–3", "0.2–0.4초"). GFM은 물결표 쌍을 취소선으로 렌더링하고, oxfmt가 `~~`로 정규화해 문서가 깨진다.
- 스펙은 결정의 기록이다. 대안 나열로 끝내지 말고 결정을 적고, 유보가 필요하면 유보 조건을 명시한다.
